# Contributing to WSUP

WSUP is a local-first workspace CLI and starter, not a shared build system or an
AI-service integration. Keep changes generic, portable, and usable without this
checkout.

## Before changing code

Read [AI.md](AI.md), the [rule index](guidance/rules/index.md), and the
[workspace model](docs/workspace-model.md). Check Git status and preserve
unrelated edits. For a defect, include a reproducible example; for a feature,
describe the intended behavior and ownership boundaries before expanding scope.

Use Python 3.9 or newer. The CLI and test suite use the standard library; no
package installation is required. Registered projects own their own dependencies
and setup.

## Go migration development

Go development uses 1.27.3 (`mise.toml`); mise is optional if that toolchain is
already available. The module is `github.com/brendenchu/wsup`. From this root:

```sh
go test -race ./...
go vet ./...
go run ./cmd/wsup --help
go run ./cmd/wsup --version
```

Use `go build -o /path/to/local/output/wsup ./cmd/wsup` to build outside the
tracked tree. Do not commit executables. A compiled binary carries its assets
and does not need Go installed; Python is still required for actual workspace
initialization, collections, and updates while the port is incomplete.

Help/version, `validate`, `projects`, `config`, `guidance`, `editor`, and Unix
`check` are implemented in Go. Every unported scaffolding command
returns exit 2 with a Python invocation hint; it never forwards automatically or
pretends to succeed. The bootstrap retains the product version 0.1.0, not a new
release or parity claim. A test checks it against the Python version authority.

Compare ported commands against the frozen scenarios with a compiled binary:

```sh
python3 -B tests/migration_baseline.py --compare-read-only /absolute/path/to/wsup
python3 -B tests/migration_baseline.py --compare-checks /absolute/path/to/wsup
```

Python drives synthetic setup and unported operations. Ported inspections must
match parsed stdout, stderr and exit codes without writes; editor output also
matches exact generated bytes and preserves pre-existing files.
Editor JSON retains Python's ASCII escaping, including Unicode surrogate pairs.
The global `--root` flag must precede the command in both implementations.
Unambiguous long-option prefixes are accepted, as in Python's argparse.
An omitted command is an exit-2 argument error; use `--help` for usage.
Malformed JSON/UTF-8 is rejected with exit 2 and no success output. Native
parser/runtime diagnostic wording is an approved difference, not a byte-parity
requirement. The subset command also runs `diagnostic-cases.json`: both runtimes
must return exit 2, write a handled stderr diagnostic (no traceback), leave stdout
empty, and preserve the filesystem. Operational errors retain the `Error: `
prefix. Other golden validation messages still compare exactly.
Guidance metadata accepts colons within values and universal text newlines.
Directory scan roots may be symlinks, but descendant symlink directories are not
traversed; inspected files still must resolve within their owner.
Go intentionally sorts guidance errors lexically, preserving duplicates, rather
than using Python's filesystem traversal order. The fixture comparison sorts only
Python's expected errors and checks Go's actual order.
Current assertion mappings live in `testdata/python-baseline/go-coverage.json`;
the original Python test inventory remains frozen. Run both the Python migration
tests (reference integrity) and Go tests (actual assertions) when changing mappings.

Native `check` requires repeatable `--project`; optional repeatable `--check`
selects named checks, and `--timeout` overrides per-check and workspace timeouts.
Selections are validated completely and deduplicated before any commands or
reports run. Dependencies are not selected implicitly. Required failures/skips,
launch errors, and timeouts return 1; configured report findings return 0 unless
other checks fail. Ctrl-C cancels the active check, skips remaining checks, writes
the report, and returns 130. Invalid input or report-writing failure returns 2.
Output stays transient; `--show-output` prints only retained output to the
terminal, never to reports.

`{python}` resolves exact argument tokens through `python3` on PATH, with a missing
interpreter recorded as a launch error. Explicit tool commands do not perform
Python lookup. The original, unsubstituted argument array defines command identity;
hash bytes retain Python's default JSON spaces and ASCII escaping.
Native reports use schema 2 and `runtime.go`, `runtime.os` (Go OS name),
and `runtime.arch`, rather than claiming a Python CLI runtime.
It stores typed status/metrics, input hashes, original-command hashes, selection,
configuration sources, and optional Git evidence, but no raw output, environment,
or command arguments. Missing Git is explicitly unavailable; an unknown dirty
state is null, not clean.

JSON and Markdown files are created exclusively with mode 0600 on POSIX; Windows
mode bits do not establish equivalent ACL privacy. Collisions never overwrite
existing files. Failed later writes return an error naming the affected path and
may leave a partial report pair; report creation is not transactional. Directory
containment is checked again at write time, and rooted filesystem handles confine
writes to the workspace and opened report directory. These checks do not make
the whole workspace policy atomic against concurrent directory replacement.
Existing Python reports are unchanged; no reports are rewritten or migrated.

The Unix runner executes literal argv with null stdin, captures each output
stream up to the configured byte limit, and counts all drained bytes. Output
decoding preserves Python's UTF-8 replacement behavior, including split retained
characters. A check gets a new session/process group; cancellation or timeout
kills that group and waits for the immediate process. Signal exits use negative
signal numbers. After the parent exits, inherited pipes receive a 200ms drain
grace before group cleanup, then another 200ms before forced pipe closure.
Cleanup failures are explicit errors, never successful results. Descendants that
deliberately escape the process group are not guaranteed to be terminated;
retained pipes still cannot hang the runner. This is process supervision, not
isolation of untrusted programs.

Runner tests cover literal arguments/current directory/null stdin, exact output
limits/counts, launch errors, nonzero/signal exits, timeout, cancellation,
descendant heartbeat shutdown, and inherited/escaped pipe retention. Unix
behavior is verified on macOS ARM64. Non-Unix execution refuses to launch until
equivalent descendant cleanup is implemented; Windows is not certified by
cross-compilation. Compiled CLI tests send real SIGINT and verify status 130,
cancelled/skipped report results, and stopped descendant heartbeats.

The native parser intentionally validates options before help/version:
`--help --invalid` fails with exit 2 instead of Python's immediate help success.
Normal help/version and valid option abbreviations remain supported; a dedicated
Go test covers this approved difference rather than weakening Python expectations.

The approved native installation target is a separately installed binary with
embedded templates. Native-generated workspaces will retain state/reports, not a
platform executable, Python runtime, or copied catalogue. Phase 5 is in progress:
`init`, `collections`, and `update` are still disabled in Go while starter
instructions and migration safety are ported.

Template-state groundwork recognizes Python schema 1 for read-only inspection
and native schema 2 for future output. Schema 2 cannot own files under `.wsup/`;
that directory holds state/reports rather than template-owned runtime content.
State validation rejects malformed paths/hashes, unknown schemas/fields,
file/parent collisions, invalid selections/omissions, and symlinked state paths.
It preserves exact input bytes for later concurrent-change checks and never
replaces stored baseline hashes with current customized file hashes. Encoding
native state does not silently convert Python ownership. No native migration
or downgrade is implemented yet; preserve a reviewed pre-migration snapshot.

The native content-update planner is also read-only and not yet exposed by the
CLI. Given a selected bundle and native state, it classifies writes,
customization conflicts, explicit keeps, and retained orphans in stable path
order. Missing managed files remain conflicts; omitted home scaffolds, user
registry bytes, reports, local settings, and unknown project files are preserved.
An explicit keep suppresses a conflict only for that preview, without accepting
the current file as a new baseline. Symlink destinations, non-directory parents,
unavailable/invalid bundles, and Python state fail explicitly. Rooted reads
confine inspection, but planning is point-in-time evidence, not an apply-time
race guarantee.

The native apply service now plans and blocks on all conflicts, rechecks exact
state bytes and observed file hashes/types before the first write, and rechecks
each destination before writing it. New files use exclusive creation; existing
files use same-directory temporary files and rename rather than truncation.
State is replaced last, retaining kept baseline hashes, collection selections,
home omissions, and original registry ownership. Orphan content is retained but
is no longer managed, matching Python updates. A final state recheck refuses
concurrent state changes during content writes.

This is not a multi-file transaction: an I/O failure can leave partial content or
new directories with old state, and errors explicitly report that possibility.
Rooted operations contain paths, but concurrent writers can still race after a
per-file recheck; concurrent mutation is not an isolation guarantee. There is no
fsync/power-loss durability guarantee. Native apply is tested with synthetic
schema-2 workspaces only and is not exposed by the CLI. Native starter adaptation,
initialization, legacy migration, and Python runtime retirement remain pending.

`src/templates/` remains the authoritative starter catalogue. During coexistence,
`internal/catalogue/assets.zip` is a generated, deterministic snapshot embedded
in the Go binary. Refresh it after any starter change:

```sh
go generate ./internal/catalogue
go test ./internal/catalogue/...
```

Generation includes hidden files, excludes Python caches, rejects symlinks, and
preserves exact asset bytes. Tests compare the complete embedded inventory to
source; normal builds/tests never silently regenerate it. This archive is not
another editable catalogue. At cutover, move the authoritative templates once
and retire the transitional archive/generator. Do not move the Python runtime
or tests while they remain the reference implementation.

## Making a change

- Edit authoritative implementation and templates in `src/`, not generated
  `.wsup/` output. Preview `python3 -B src/wsup.py update` to refresh the local
  installation; preserve source-specific docs with explicit `--keep` decisions.
- For CLI documentation, compare `--help` and the implementation with the
  workspace model's command reference. Keep the root and
  `src/templates/workspace/docs/workspace-model.md` copies identical. Change
  starter docs at their source, then refresh generated `.wsup/` output through
  preview/apply; do not edit its state hashes by hand.
- Inspect the implementation, callers, and tests before editing.
- Keep behavior changes focused and add regression coverage for observable
  behavior. Update directly related documentation.
- Keep workspace-owned and independent project repositories separate.
- Keep each workspace self-contained, describing only itself and its descendants.
  Never write upward workspace relationships into descendant documentation or
  make local guidance depend on context outside its root.
- Root `guidance/rules/` and `.agents/skills/` are canonical. Keep their
  corresponding copies under `src/templates/workspace/` synchronized.
  Development guidance routes to local rules, not the distribution catalogue.
- Keep durable documentation with its owning project, use one canonical copy,
  and link rather than duplicate. Visible `workbench/` drafts may be tracked
  locally after review; do not commit them automatically. Keep restricted
  records outside documentation and Git, and promote approved knowledge to
  maintained docs.
- Template and skill changes affect generated output. Review a disposable
  generated workspace and ensure its own CLI can generate another workspace.
- Keep machine paths, credentials, provider assumptions, and framework-specific
  setup out of the generic starter.

## Verification

From this repository's root, run:

```sh
python3 -B src/wsup.py validate
python3 -B src/wsup.py guidance
python3 -B src/wsup.py check --project wsup --show-output
git diff --check
```

For a focused test run, use the existing unittest runner:

```sh
python3 -B -m unittest discover -s tests -p 'test_services.py'
```

The [Python migration contracts](testdata/python-baseline/README.md) preserve
synthetic command behavior and inventories from the immutable checkpoint.
Normal tests replay committed expectations; they never recapture them.
Run `python3 -B tests/migration_baseline.py --verify-archives` to verify their
provenance against the recorded Git commits before using them for the Go port.

The configured suite covers standalone generation and update safety. Check
reports are local under ignored `.wsup/reports/`; keep development notes and
disposable artifacts in ignored `workbench/.local/`. Use temporary destinations outside
the source tree for manual generation and upgrade exercises; never overwrite
real user workspaces to test changes.

Report the interpreter, operating system, checks performed, and any skipped
coverage. Structural skill validation is not proof of client discovery or
invocation. See [AI guidance](docs/ai-guidance.md) for discovery and compatibility
limits. Keep session logs, implementation plans, and disposable investigation
material under ignored `workbench/.local/`; public documentation should describe the
product and its use.

## Preparing a contribution

Explain what changed, why, compatibility effects, and verification results.
Review the full diff, including new files. Keep local settings, reports, secrets,
and unrelated formatting out of the contribution.

Add user-visible changes to the Unreleased section of [CHANGELOG.md](CHANGELOG.md).
Ordinary contributions do not need a version bump or tag; maintainers group
changes into releases using the [release guide](docs/releases.md).

Contribute only material you have the right to submit under the repository's
[MIT license](LICENSE). This guide does not transfer copyright ownership.
